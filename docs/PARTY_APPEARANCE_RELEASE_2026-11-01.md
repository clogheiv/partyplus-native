## Working product

Create or Edit a party and open optional **Party appearance**. Start with PartyPlus original, casual, birthday, cookout, holiday, shower or game-night designs, then choose coordinated artwork, six readable accent palettes, three typography choices and illustrated, photo or elegant layouts. Changes update the shared invitation preview immediately. Skipping customization gives the original branded PartyPlus design. The owner's authentic icon/banner remain intact; six new themed illustrations are original inline SVG, with existing self-hosted fonts and no remote asset service.

Appearance is saved with the party through the existing verified-host, revision-controlled, replay-safe commit. My Parties thumbnails, party pages and direct browser invitations use the same choices. Guests see the saved design and keep their existing RSVP/bring behavior; they cannot edit the appearance or upload party images. Existing parties need no migration or user action to keep working.

Personal photos are decoded and re-encoded locally to JPEG, up to 1600px on the long edge and **1,500,000 bytes**, stripping source metadata. Accepted source formats: JPEG, PNG or WebP, up to 20 MB / 48 megapixels; HEIC requires a JPEG conversion. Simple horizontal/vertical positioning and zoom use the same 4:3 frame in the editor, invitation and thumbnail. Text stays separate from photos for contrast. Binary drafts survive refresh and email sign-in in IndexedDB; large base64 images are not stored in localStorage.

A new photo requires a verified host-bound upload slot and immutable opaque UUID path on the existing Supabase project. Upload retries never overwrite: duplicate/uncertain results require exact fetched-byte SHA256 correspondence. The server checks owner, party, object presence, JPEG MIME and size before accepting the image reference. Appearance receipts must match the submitted choice before pending state is cleared. If a new local photo draft has been evicted, Save stops before a party mutation and asks the host to choose it again or remove it; other details remain preserved. Existing saved cloud photos do not require a new local blob. This final narrow guard was typechecked and code-reviewed; browser eviction itself was not fault-injected.

## Photo visibility and resource protection

The photo bucket is **public by known, unguessable photo URL**. Anyone with an invitation or retained photo link may view the image. This is not private or immediately revocable storage. There is no bucket/object-list permission, no overwrite policy, and no guest/stranger upload/delete capability. The visibility notice is shown before the picker. Recipient copies and caches may outlive removal.

After a confirmed replacement/removal, owner-bound cleanup persists a small retry queue. A server removal intent first prevents re-adoption of an unreferenced image, then Storage removes its bytes, then the server releases its capacity slot. Referenced images cannot be retired. Failed cleanup does not turn a successful party save into failure; the same account retries on return. Removing an image from an invitation can precede completion of this cleanup, so an older URL may temporarily remain accessible.

Conservative media resource safeguards cap unreleased reservations at 160 total / 40 per principal / 8 per party, a worst-case 240 MB allocation. Released slots count as free only after the object is absent. These are storage safety budgets, **not paid hosting limits or eligibility**; capacity feedback offers gallery artwork or cleanup. Existing organization storage/egress headroom was checked; no paid transformation, Edge service, overage, plan change, new external service or charge was enabled.
