## Delivered

- Visible mobile **Sign in** opens **Sign in to your account**, with email/password selected and email code beside it. Existing-account code access never creates an account; account creation is explicit. Initial new-account verification offers optional **Create a password** with an explanation about other devices. Anonymous guests see existing-account access and an explicit warning before ending their guest session: guest responses/claims are not merged and may become uneditable. Guest RSVP remains account-optional.
- Host-only **Manage party** sits beside the main party actions and contains **Edit party** and **Delete party**. Confirmation states: **This removes the party and its invitation for everyone.** Server deletion makes fresh invitation/list access unavailable; it retains underlying rows for recovery rather than physically erasing them.
- **Past parties** opens a separate view; **Back to active parties** preserves Hosting/Joined selection and search. Classification compares the saved date/time strictly before now. Equal, undated or invalid timestamps remain active. Local clock/boundary updates and foreground list refresh avoid periodic backend polling. Rescheduling into the future returns a party to Active; classification never deletes or rewrites party data.

Actual disposable staging deletion exposed an existing browser acknowledgement mismatch. The server correctly returned `{deleted:true,operationId}`; the browser had expected `committed:true`. The client now requires `deleted:true` and the exact durable operation UUID, accepting a successful replay and retaining pending state for false/malformed/mismatched acknowledgements. No server/API signature/schema/permission change was needed.
