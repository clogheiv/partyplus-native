# PartyPlus production security rollout proposal

Review only. Production `typbofemqhjoiwbkdvuc` is unchanged. Only isolated staging `qmbwrbxbbshbavfhkujx` and synthetic loopback databases were written. Michael must separately approve each production phase; an approval of this document does not authorize store publication, a website deployment, destructive recovery, or spending.

## Recommended decision

Approve a **time-bounded legacy write freeze**, followed by a separately gated verified-contract cutover. Retaining unsafe writes while waiting for every device/recovery gate leaves the confirmed vulnerability open. The freeze changes authorization, not customer rows. Existing clients can still read; all legacy saves, RSVPs, claims, suggestions and deletes stop. Full v2 enablement is **not operationally ready** until the open device, delivered-email, hosted recovery and release gates below pass.

The freeze intentionally preserves the three existing unrestricted SELECT policies temporarily. Consequently, existing raw enumeration exposure remains during that period. It does not expand reading access. Set a cutover deadline before executing phase 1; my recommended maximum compatibility window is seven days, with daily readiness review. If readiness remains blocked, retain the write freeze and obtain a decision on closing raw reads; never reopen unsafe writes. Existing invite URLs and party IDs are retained throughout.

## Exact artifacts and database effects

The executable review files are under [`supabase/production-proposal`](../supabase/production-proposal). [`manifest.json`](../supabase/production-proposal/manifest.json) records SHA256 of every file and the authoritative metadata snapshot. [`prepare-security-package.mjs`](../scripts/prepare-security-package.mjs) regenerates these files locally and performs no remote calls. They contain no synthetic Auth schema or production data copies.

| Phase | Exact file | Proposed effects |
| --- | --- | --- |
| 1 | `01-freeze-legacy-writes.sql` | Transactionally assert baseline columns, constraints, policies, owner and RLS; lock the three tables; drop the eight named unconditional INSERT/UPDATE/DELETE policies; revoke ALL table privileges from PUBLIC/anon/authenticated and regrant only the preexisting anon/authenticated SELECT; remove column grants, including potential maintenance privileges; create nine restrictive deny-write policies; assert effective inherited/column privileges are safe; preserve the three existing SELECT policies. |
| 2 | `02-install-verified-contract.sql` | Recheck columns/constraints and freeze policies; add revision, deleted_at, date, location, theme, claimed_by_user_id and created_by; backfill canonical date/location from existing fields; retain all IDs, original columns, constraints and UUID types; add `(party_id,id)` item index and date/location alias trigger; create private host evidence, receipt and release-control tables; remove all legacy policies and direct table grants; install the seven v2 RPCs and private helpers. Initial v2 writes are **paused**. |
| 3 | `03-enable-verified-writes.sql` | Set the private singleton release gate to true after acceptance evidence and separate approval. No customer-row rewrite. |
| 4 | `04-safe-rollback-pause.sql` | Set the same gate to false. Reads and host listing continue; already committed operations replay their exact receipts; all new v2 mutations raise `writes_paused`/55000. Unsafe legacy policies stay absent. |

The eight policies removed in phase 1 are `public insert parties`, `public update parties`, `public insert party_items`, `public update party_items`, `public delete party_items`, `public insert party_rsvps`, `public update party_rsvps`, and `public delete party_rsvps`. The retained policies are `public read parties`, `public read party_items`, and `public read party_rsvps`.

Phase 2 grants anon/authenticated EXECUTE only on `partyplus_v2_read_party(text)`. Only authenticated receives mutation RPCs (`commit_party`, `rsvp`, `claim_item`, `suggest_item`, `delete_party`) and `list_host_parties`. A signed anonymous guest uses the authenticated database role, but server verification checks `auth.users` and refuses anonymous/unconfirmed host actions. A verified stranger has no host ledger grant. A party ID, old device UUID, hostId payload or user metadata never constitutes ownership proof. Guest RSVP IDs come from the authenticated principal; callers cannot choose another guest's ID. Legacy claim labels are retained and cannot be stolen by claiming an unlabeled principal.

All definers have fixed `search_path=pg_catalog`; tables/private helpers/release controls are inaccessible to client roles. The existing `set_updated_at()` trigger function receives a fixed search path and loses client EXECUTE. Future object defaults **for the executing migration owner** lose client table/sequence grants in public and function execution defaults. PUBLIC's global function EXECUTE default is revoked globally for that owner because a schema-local revoke cannot undo a global grant. Existing unrelated grants, managed Auth/storage schemas, `supabase_admin` defaults, and realtime publications are unchanged. Other creators must follow explicit grants; do not assume owner-specific defaults protect future objects created by another role. Service credentials remain privileged and must never be placed in clients.

Every file requires an explicit operator session setting for its reviewed phase (`freeze-v1`, `cutover-v2`, `enable-v2`, `pause-v2`) plus `partyplus.target_project`. These settings are accidental-execution guards, **not proof of user approval or server identity**. Confirm the actual dashboard/connection reference and approval record independently. Use a controlled owner session with errors fatal; run one file at a time; clear these settings afterward. Transactions have five-second lock and sixty-second statement limits. An error must roll back the entire phase. Size/backfill duration on real data is unknown; if the approved migration cannot meet the bounded window, stop and revise the plan instead of silently increasing limits. Checksums use UTF-8 with CRLF normalized to LF, as specified in the manifest.

## Legacy impact and upgrade strategy

Latest EAS store-distribution source is `d1972a0a762b71e71869fe9dd230f29adc1c3184`: iOS 1.0.3/build 15 and Android 1.0.3/versionCode 12. Its `src/data/parties.ts` creates with direct upsert, edits a party then deletes/replaces entire child collections, and deletes RSVPs/items before the parent. Those exact operation classes are denied in the freeze. Production metadata has no parent DELETE policy: the old aggregate delete can remove children while retaining a parent. The proposed revocations block its first child delete and prevent that partial loss.

| Client/operation | Freeze | Verified cutover |
| --- | --- | --- |
| Unchanged legacy native/web raw reads, known-ID reads, host/device filters | Existing SELECT behavior retained | Raw reads denied; native upgrade needed; validated v2 web known-ID reader preserves invitations |
| Legacy party create/edit, collection replacement, RSVP, claim, suggestion, delete | Denied, including verified host's old direct calls | Denied permanently |
| v2 known-ID invitation read | Unavailable until contract installed | Works unsigned; same party IDs and link aliases |
| v2 verified host create/edit/delete | Contract not installed | Works only after release gate opens and ownership check passes; delete is a recoverable tombstone |
| v2 guest RSVP/suggestion/claim | Contract not installed | Signed principal acts on its own RSVP/claim; no host collection replacement |
| Legacy ownership bridge | No change to original host_id/cache | Grant verified principal only after independent reviewed proof; preserve original host_id and evidence reference |

There is no way to inject a new upgrade prompt into an unchanged installed binary. Its existing cloud-error behavior may be confusing; do not claim a graceful upgrade screen for 1.0.3. Prepare the website notice and next client release before the freeze; show: **“PartyPlus has paused changes in older versions to protect your party. Your saved data is preserved. Update PartyPlus; guests can use the invitation website.”** During the initial freeze the website must also explain that responses are paused until the safe service is ready. Do not advertise working web RSVP before the v2 contract is enabled.

The candidate client now recognizes `writes_paused` and retains durable drafts/outbox IDs through restart and retry. Its account screen permits resending/correcting email and does not reuse a consumed OTP after a host-list failure. Strong upgrade notices in the new client/site are required; a forced version check in new code alone cannot stop old binaries. The database is the enforcement boundary. Do not add a permissive legacy write exception or infer grants from cached device IDs to shorten the bridge.

Prepare native previews under isolated `.preview` identities, preserving production package `com.partyplus.app`, bundle identity and scheme `partyplusnative` for the separately approved release. Compare the current store versionCode/buildNumber and signing provenance before selecting increments. Cross-device verification uses synthetic staging identities. Existing production installs must never be used to create test parties against live production. A store-to-modernized upgrade needs signed, staged distribution under the eventual production identity with a staging backend; a separate preview install cannot prove preservation of the real app's sandbox, signature or cache.

1. **Before phase 1:** Refresh catalog metadata read-only and compare the manifest/preflight; record activity estimates and deployment/binary provenance without copying customer content into fixtures. 2. **Freeze:** Execute only file 01 in the approved owner session. Capture catalog metadata/ACL results and ordinary operational telemetry. Synthetic write probes remain in staging; do not run exploit probes or test writes in production. Acceptance: exactly three read policies plus nine restrictive write denies, zero effective mutation/column grants for anon/authenticated, unchanged row counts/IDs verified by the approved operator, no unexpected table owner/trigger/function drift and no partial child deletion mechanism. Any transaction error is a no-go.
3. **Compatibility period:** Qualify native/device previews, hosted invite fallback, delivered OTP signup/link/recovery, session expiry, independent host/guest behavior, legacy upgrade and hosted restore. Establish recovery staffing and evidence procedure for old hosts. Prepare release/store approvals separately. 4. **Contract install:** With separate approval and backup checkpoint, run file 02. Keep writes paused. Approved operational validation must confirm columns/aliases/types, host evidence/receipt/RLS/grants/function ownership/search paths, raw table denial, valid known-ID reads and preserved customer totals. No production synthetic fixtures. Publish the qualified v2 web/client through separate approval, preserving existing links and package identities.
5. **Enable:** Only after all full-cutover gates pass and separate approval, run file 03. Monitor save acknowledgments/conflicts, guest responses and host recovery by operation IDs without logging OTPs, tokens or customer content. Review at 30 minutes, 24 hours and seven days. A rise in unexplained failures, data/claim loss, wrong ownership or unconfirmed saves triggers file 04 and incident investigation.

Full-cutover acceptance requires: physical iOS+Android Create→Save→Invite→Open→RSVP/Claim→host sees→return loop; installed old-to-new data/cache/signature/version verification; Safari/Chrome cold/warm installed/uninstalled links; two independent guests and host edit preservation; offline/kill-after-uncertain-save replay without duplication; verified email delivery and correct Token templates; anonymous email_change preserving the exact principal; expired/wrong/replayed OTPs denied; verified host recovery on another device; stranger/old UUID denials; rehearsed hosted restore with usable Auth and preserved receipts; documented recovery time/data-loss objective; backups and support coverage. SQL correctness has passed staging, but these physical/mail/hosted-recovery gates are still open.

## Rollback and recovery prerequisites

Before touching production, record a verified recoverable backup timestamp, encryption/access custody, exact database schema/RLS/grants/functions/defaults/trigger manifests, and restore rehearsal evidence. Include application rows, `auth.users`/identities needed to preserve UUIDs, host access evidence, operation receipts, release controls and tombstones. Export roles/default ACLs and migrations independently; production currently has no migration ledger. Preserve hosting/build/environment configuration, redirect rules, Auth templates/SMTP/provider settings and any storage objects separately. A green backup timestamp is insufficient. Agree and measure recovery-time and recovery-point objectives before acceptance; no unmeasured promise is made here.

For a **manual restore to another hosted project**, follow the current [Supabase backup/restore guidance](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore), including roles, managed-schema customizations, migration history, external settings and any encryption-root/Vault considerations. Restore the synthetic staging archive into an isolated destination; compare IDs/rows, effective privileges, evidence, receipts and aliases. Sign in through destination Auth and list the same host grants; replay a pre-backup operation; deny stranger and unsigned mutations. Test a fresh/expired session rather than assuming source-project JWTs remain valid. A logical same-cluster PostgreSQL restore is proven; cross-project managed Auth restore is not.

At phase 1, rollback means retain the safe read-only freeze and repair compatibility/communications. **No reverse SQL restoring true write policies is supplied.** At phase 2/3, run file 04, keep all additive fields, IDs, data, receipts and evidence, and roll forward a corrected contract or return the client/site to the last v2-compatible artifact. Receipt replay returns its earlier authoritative snapshot; the client must reread current state before a new edit. Mutations hold a shared release-control row lock through transaction completion, so pausing waits for in-flight mutations to commit/roll back before the pause commits. The independent PostgreSQL test observes the pause waiting on that lock; after pause commits a new mutation is denied. If the bounded pause times out, it has not taken effect: investigate/drain and retry the reviewed pause. If an RPC itself is suspected compromised, owner must additionally revoke that exact RPC EXECUTE in a separately reviewed incident action; the normal gate is not a substitute for revoking a vulnerable function.

Do not downgrade to unsafe legacy clients as a database rollback, drop columns/private ledgers, purge tombstones/users/receipts, or restore an old snapshot over newer accepted operations. Destructive recovery and real-data reconciliation require separate approval. Restoring a backup includes restoring the hardened ACLs and paused gate before making it reachable.
